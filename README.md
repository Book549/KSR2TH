# KSR2TH

**S'gaw Karen Translator Using a Rule-Based**

No model. No training. Segment → tag → look up → apply grammar rules → assemble.
Every output word comes from a dictionary row or a documented grammar rule, and the
translator can tell you which, for every token.

```bash
pip install -r requirements.txt
python rule_translate.py --text "ผมไม่ชอบกาแฟ"
python rule_translate.py --text "..." --explain
python rule_translate.py --interactive
```

`rules/lexicon.csv` is committed, so the translator runs straight away. Rebuild it
from the dictionary workbook only if the workbook changes:

```bash
python build_lexicon.py Sgaw_Karen_English_Thai_Dictionary2.xlsx
```

`pythainlp` is optional. Without it the translator falls back to a dictionary-driven
longest-match segmenter, which is the same pipeline with worse word boundaries.

`evaluate_rules.py` needs `sacrebleu` and the `generated_dataset/` splits from the
companion neural project; those are not part of this repository. The last recorded
run is in `outputs_rules_eval.json`.

## Why this suits the task better than the neural model

Thai and S'gaw Karen agree on nearly all the word order that normally makes rule-based
translation hard:

| | Thai | S'gaw Karen |
|---|---|---|
| clause | Subject-Verb-Object | Subject-Verb-Object |
| modified noun | Noun + adjective | Noun + stative verb |
| counting | Noun + numeral + classifier | Noun + numeral + classifier |
| place | preposition + place | preposition + place |
| verbs | no inflection | no inflection |

So translation is close to **monotone** — mostly word-for-word, with a small number of
insertions. That is exactly the case transfer rules handle well, and it is why this can beat
a neural model trained on a corpus with no real sentences in it.

The genuine differences are the rules:

- **Negation is a circumfix.** Thai marks it with one pre-verbal word; Karen needs `တ` before
  the verb *and* `ဘၣ်` closing the clause — a particle with no Thai counterpart.
- **`ไป <place>` needs an allative** `ဆူ` inserted.
- **Thai politeness particles** (ครับ, ค่ะ, นะ …) have no Karen equivalent and are dropped, with
  a note, rather than guessed at.

## Results, measured on the same files the model uses

| | `test.jsonl` (template grammar) | `test_unseen_vocab.jsonl` |
|---|---|---|
| BLEU | 58.9 | **73.0** |
| chrF | 77.6 | **83.8** |
| exact match | 50.1% | 66.6% |
| dictionary coverage | 90.9% | 97.9% |
| fully-covered sentences | 68.6% | 93.6% |

(Figures as recorded in `outputs_rules_eval.json`, measured with `pythainlp` installed.)

**The second column is the important one.** Those are sentences built from words held out of
neural training entirely. The rule engine has no train/test distinction — it never "learned"
anything, so held-out words are just ordinary dictionary words to it. A neural model, by
construction, cannot emit a word that was absent from its training data; run the companion
project's `evaluate.py` on that split to see its number next to this one.

On `test.jsonl` the neural model scores higher (BLEU 95.9). That split is generated by
the same templates it trained on, so it is measuring recall of memorised sentences. Note also
that the rule engine's *lower* score there is partly the noisy rows — that split contains
deliberate typos, which a dictionary lookup handles worse than a model does.

## Architecture

```
rules/
├── lexicon.csv          3,446 Thai headwords · 6,871 senses  (built from the workbook)
├── lexicon.py           lookup, POS-aware sense selection, provenance on every entry
├── core_lexicon.py      ~120 hand-verified high-frequency words that OVERRIDE the bulk data
├── grammar.py           Karen particles, Thai function words, the transfer rules
├── names.txt            proper names to copy through — user-editable
├── translator.py        Thai → Karen: the pipeline
├── reverse_lexicon.py   Karen → Thai index, candidates ranked by Thai word frequency
└── reverse.py           Karen → Thai: segmentation, sense choice, rule inversion
```

### The core lexicon exists because the bulk data fails on common words

Found by testing, not by reasoning:

```
ผม  → "hair"          Thai ผม is both "I" and "hair"; every workbook sense is the noun,
                      so the pronoun reading isn't there to be found
มี  → ပၥ်ဃုၥ်          four senses all rated H, plain "have" (အိၣ်ဒီး) is fourth —
                      confidence order cannot break the tie
ไป  → လၢကျဲ ဒီဘိ       the workbook's ไป rows are all adverbial ("along the way");
                      the plain verb "go" is not among them
```

A word-for-word translator lives or dies on these, because they carry the grammar. ~120 words
are pinned in `core_lexicon.py` and consulted first. Every one is the same hand-verified mapping
used by the companion neural project's `dataset/templates.py`, whose `KAREN_WORD_SOURCES` table
records the English headword, confidence rating and source codes.

### Unknown words are passed through and flagged

```
TH  สวัสดี วันนี้อากาศเป็นอย่างไรบ้าง
KR  สวัสดี တနံၤအံၤ မူခိၣ်ကလံၤသီၣ်ဂီၤ မ့ၢ် อย่างไรบ้าง
    coverage 50%
    ! not in the dictionary, passed through as Thai: สวัสดี, อย่างไร, บ้าง
```

Untranslated Thai is emitted **without spaces**, which is how Thai is written: an unknown word
reads as one word. The notes list the missing items separately, so the output stays readable
while the report stays precise.

The reader sees exactly which words are missing, and the report tells you which dictionary rows
to add next. Every failure is a work item, not a mystery — and unlike the model, adding a row
fixes it immediately with no retraining.

## Six bugs found by testing this

1. **`ไม่ชอบ` glued into one lexical entry.** The workbook has "ไม่ชอบ" (dislike) as a headword, so
   the segmenter kept it whole, negation got resolved *lexically*, and the clause-final `ဘၣ်` was
   never emitted. Fixed by removing ไม่-/จะ- prefixed headwords from the segmenter's word list, so
   negation always goes through the grammar rules.
2. **Negated future put the marker in the wrong place.** `เขาจะไม่ไปโรงเรียน` produced
   `... တ လဲၤ ဆူ က ကၠိ ...` — the future prefix drifted past the verb and attached to the following
   noun. Both particles are documented as sitting "immediately before the verb" and no source
   resolves their order, so the negation is applied (dropping it would reverse the sentence) and
   the future is reported as unmarked.
3. **Numbered sense lists leaked into output.** Karen cells like `၁ ကွၢ်ဃု, ဃုထံၣ် ၂ ထံၣ်န့ၢ်က့ၤ`
   are numbered sense lists; splitting only on commas left the digits in, so `ตก` translated to
   `၁ လဲၤလီၤ ၂ လီၤစၢၤ`. Only the first numbered sense is kept now.
4. **Proper names split and half-translated.** `สมชาย` segments into `สม` + `ชาย`, and `ชาย` is a
   real word ("male") — so half the name got translated, which is wrong in a way that is hard to
   spot. `rules/names.txt` holds names to copy through; **add to that file when you meet a new
   name.** Thai has no spaces and nothing marks a name as a name, so a list is unavoidable.

5. **Unknown words were shredded into single characters.** Without `pythainlp`, the fallback
   segmenter emitted one character at a time whenever nothing matched, so `สวัสดี` — a greeting
   with no bare headword in the workbook — came out as the six tokens `ส ว ั ส ด ี`, and a lone
   vowel mark is not a word in any script. Uncovered characters are now kept together as **one**
   token: the matcher runs forward to the next position that starts a dictionary word of at least
   three characters, and anything before it is a single unknown word. The three-character floor is
   what stops `ดี` ("good") from cutting the greeting in half, and a one-character floor on the
   unknown piece itself stops `ย่าง` from leaving a bare `อ` behind in `อย่างไรบ้าง`.
6. **The fallback segmenter did not know the function words.** `_known()` consulted only the
   dictionary, while the `pythainlp` path was separately seeded with the grammar's particle lists.
   So without `pythainlp`, `จะ` was not a word: `เขาจะไปโรงเรียนพรุ่งนี้` produced an unknown
   `จะไป` instead of a future marker and a verb, and `ไม่ชอบ` survived whole — reintroducing bug 1
   on that path. Both paths now build from one word set (`_segmenter_words`), so they agree on
   what a word is.

Also handled: `กินข้าว` came back as one unknown compound even though both halves are in the
dictionary. Unknown tokens are now re-split against known words, but *only when every piece is
known*, so a genuinely unknown word is never chopped into misleading fragments.

## What it cannot do — plainly

- It translates word by word with local rules. **There is no model of meaning.** It will not
  resolve an ambiguous word from context beyond its part of speech.
- Long or complex sentences — relative clauses, coordination, embedded speech — pass through
  largely word-for-word. Usually understandable, not fluent.
- **Coverage is bounded by the dictionary: 3,446 Thai headwords.** Ordinary Thai has far more.
- **Yes/no questions cannot be marked.** The Grammar sheet documents a Karen polar-question
  particle phonemically (IPA /ha/) but no script form exists anywhere in the workbook's 22,543
  rows. The particle is dropped and the sentence flagged.
- Roughly **one in four** of the BFAS-APK-sourced entries may carry a character-level error
  (~77% decode accuracy, documented in the project notes). Every output row carries its source
  confidence so you can see when you are standing on one.
- **Without `pythainlp`, word boundaries are weaker.** A short dictionary word at the start of an
  unknown one still wins: `เทคโนโลยี` ("technology") begins with `เท`, which is a headword, so it
  segments as `เท` + unknown `คโนโลยี`. Installing `pythainlp` avoids this class of split.

The honest summary: this is a **glossing engine with real grammar**, not a fluent translator. For
an educational tool where a visible gap is far better than a confident wrong sentence, that is
the right trade — and it gets better every time you add a dictionary row.

# S'gaw Karen → Thai (the reverse direction)

```bash
python rule_translate.py --direction kr2th --text "ယ တ ဘၣ်သး ခီဖံၣ် ဘၣ်"
python rule_translate.py --direction kr2th --interactive
python rule_translate.py --direction kr2th --text "..." --explain
```

```
KR  ယ တ ဘၣ်သး ခီဖံၣ် ဘၣ်                    TH  ผมไม่ชอบกาแฟ
KR  အဝဲပိၥ်ခွါ က လဲၤ ဆူ ကၠိ ခဲမုၢ်ဆ့ၣ်      TH  เขาจะไปโรงเรียนพรุ่งนี้
KR  အဝဲပိၥ်မုၣ် တ အိၣ်ဒီး သိလ့ၣ် ၂ ဖျၢၣ် ဘၣ်  TH  หล่อนไม่มีรถยนต์สองคัน
KR  န လဲၤ ဖဲလဲၣ်                              TH  คุณไปที่ไหน
```

## This is not the forward translator run backwards

Three things genuinely differ, and each needed its own solution.

**1. There is no segmenter for Karen.** No pythainlp equivalent exists — no tokenizer, no tagger,
no corpus. Karen is written with spaces, but they mark phrase boundaries as much as word
boundaries, and a multi-word dictionary entry can span them. Segmentation is therefore
dictionary-driven: whitespace chunks are tried in groups of three, then two, then one, and only
then is a single chunk broken up internally by longest match. Anything unmatched is kept as **one**
unknown piece rather than shredded into fragments that would each be reported as a separate
missing word.

**2. Ambiguity runs the other way, and much harder.** One Karen word maps back to several Thai
words for **513 of 6,259 headwords (8.2%)**, and the workbook gives no ordering among them — they
came from different rows. Candidates are ranked by how common the Thai word actually is, using the
Thai National Corpus frequencies bundled offline with `pythainlp` (the same corpus behind the
project's `Thai_Word_Frequency_Ranking.xlsx`).

The ranking order was decided by testing, not assumed. Sorting by confidence first *looked*
principled and picked `สถาบัน` ("institution", rated H) over `โรงเรียน` ("school", rated M) for
`ကၠိ` — the wrong word for nearly every sentence. H and M are both "attested"; between two attested
Thai synonyms the useful signal is which one Thai speakers use. So only L is demoted and frequency
decides among the rest. Alternates are reported, so a choice is always visible:

```
! 'ကၠိ' could also be สถาบัน - chose 'โรงเรียน' as the commonest Thai word
```

**3. The grammar rules invert unevenly.** Karen's negation **circumfix collapses into a single Thai
word**, so the clause-final `ဘၣ်` has to be found and deleted — which means looking ahead to the end
of the clause, not just at the token in hand. Karen's allative `ဆူ` **disappears entirely** (Thai is
`ไปโรงเรียน`, with no preposition). And Karen's one general classifier has to be **expanded back
into the right Thai classifier**, which is information Karen does not carry at all — recovered from
the noun where known (`รถยนต์` → `คัน`), falling back to the generic `อัน` with a note where not.

## Results

| | `test.jsonl` | `test_unseen_vocab.jsonl` |
|---|---|---|
| **kr2th** chrF | 72.0 | **84.1** |
| **kr2th** exact match | 40.5% | 64.8% |
| dictionary coverage | 97.4% | 98.5% |
| **round trip** th→kr→th, chrF | 87.0 | **89.1** |
| **round trip** exact match | 55.8% | 72.0% |

Read **chrF, not BLEU**, for anything with Thai on the output side: Thai is written without spaces,
so word-level BLEU is close to meaningless there.

The round trip passes through **both** rule sets, so every lossy step compounds — Karen carries no
politeness particles and only one classifier, so some Thai detail cannot survive by construction.
chrF 87–89 with over half the sentences coming back character-identical is a floor on quality, not
a measure of either direction alone.

## Extra limits specific to this direction

- **No POS tagger for Karen**, so sense selection has less to go on than in the Thai→Karen
  direction, where pythainlp's tagger narrows the candidates.
- **Thai classifiers cannot always be recovered** — Karen genuinely does not encode which one.
  Extend `THAI_CLASSIFIER_BY_NOUN` in `rules/reverse.py` to cover more nouns.
- **Politeness is gone for good.** Thai ครับ/ค่ะ are dropped going out and there is nothing in the
  Karen to bring them back, so translations read blunt by Thai conventions.
- Output is joined **without spaces**, which is correct written Thai.
